# Analysis and Reflection (lab §14)

**1. What prevented another person from reproducing the previous project immediately?**
The notebook read an unversioned CSV from its working directory, with no checksum and no dependency list (only "Python 3.13.9" in the metadata). Its results depended on things nobody wrote down: pandas' default NA strings (346 cities literally named "N/A" become missing and then "Unknown"), the order of cleaning steps (de-duplication before the unit filter, keeping the first row in file order), and the row order after the pivot, which decides the stratified split. Cells had to be run manually, top to bottom. There were no saved intermediate datasets, so a different result could not be traced to a step, and the metrics existed only as printed text. Details: reproducibility report §2.

**2. Which artifact is the authoritative source, and what is the role of each?**
The **original file** (`data/source/world_air_quality.csv`, identified by its sha256 in the manifest) is the single authoritative source. Everything else can be regenerated from it. The **raw ingested copy** is a lossless, queryable landing of that file (verbatim strings plus lineage columns). It is authoritative for *what was ingested and when*, but not for content. The **curated dataset** (`station_day_pollutants`) is the authoritative *data product*: the cleaned, business-level table other consumers should use. The **model-ready dataset** is a derived, model-specific view (filtered rows, imputation, engineered features, label). It is an input to training, not a source of truth, and is rebuilt whenever its rules change.

**3. What identifier or rule prevents duplicates, and what assumption makes it valid?**
Per layer: raw = `(_source_sha256, _source_row_number)`; staging = `(location, pollutant, last_updated_utc)`, hashed to `reading_key`; curated = `(country_label, city, location, reading_date)`, hashed to `station_day_key`; predictions = `(station_day_key, model_name)`. Each is a PRIMARY KEY in PostgreSQL, and loads are `INSERT … ON CONFLICT DO UPDATE`. The staging rule assumes that one station reports at most one valid µg/m³ value per pollutant per timestamp, so a second row with the same key is a duplicate report (in this file, mostly the same reading in ppm and µg/m³). That holds for OpenAQ "latest value" snapshots. It would break if two different instruments at one station reported the same pollutant at the same second. It also assumes station names are stable identifiers, which is why missing names are filled with "Unknown" before keying.

**4. With no natural update timestamp, how was incremental ingestion simulated honestly?**
The checkpoint is a **source-row high-water mark** (`last_committed_row`) tied to the file's sha256, stored in `data/checkpoints/ingest_checkpoint.json` with `checkpoint_type: source_row_high_water_mark` and an explicit note that it is *not* a business timestamp. Each incremental run takes the next N source rows (default 20,000) as a batch. `_ingested_at` is labelled an audit (pipeline-time) column. If the file's checksum changes, incremental mode refuses to continue and requires a full reload, rather than pretending new rows arrived.

**5. Which transformations belong in staging versus curated, and why?**
**Staging** holds row-level conformance that does not change the grain: NA semantics, scope filter (six pollutants), type parsing (UTC timestamps), de-duplication on the sensor key, unit standardisation, removal of invalid negative values, filling missing labels, and parsing coordinates. It is still one row per reading, close to the source, and reusable for any purpose. **Curated** holds business-level reshaping: aggregation to station-day daily means and the pivot to one column per pollutant. That is the grain analysts and the model consume. Model-specific choices (requiring PM2.5/NO2/O3, median imputation, engineered ratios, the WHO label) are kept out of curated and placed in the model-features dataset, because they serve one use case.

**6. Which storage format performed best, and why not generalise?**
For full reads of these small tables, file formats were fastest (Parquet expected best; CSV close at this size). For selective analytical queries, PostgreSQL was fastest by more than 10×, because only the aggregate leaves the database. JSON was the largest, the slowest, and silently lossy at pandas' default precision. These numbers come from about 5 MB of data on one machine with a warm cache and no concurrency. They mostly measure parsing overhead, not I/O. At larger scale, or with concurrent users, updates or selective access, the ranking changes. See `docs/storage_benchmark.md`.

**7. What happens if Airflow retries the load after the database committed but the task never received confirmation?**
Airflow marks the attempt failed and runs `load_postgres` again with the same run id. The retry repeats the whole load: COPY into a temp table, upsert, scoped delete, and the load-log upsert.

**8. How does the design make that retry safe?**
(a) Each table load is one transaction, so a crash *before* COMMIT leaves nothing behind. (b) Rows are keyed by deterministic business keys with PRIMARY KEY constraints, and written with `ON CONFLICT DO UPDATE … WHERE row_hash IS DISTINCT FROM EXCLUDED.row_hash`, so replaying the same snapshot inserts 0 rows and updates 0 rows. (c) The full-sync delete removes only keys absent from the snapshot, which also yields 0 on a replay. (d) `audit.load_log` is keyed by `(run_id, table, scope)` and upserted, so retries do not add log rows. This was demonstrated by re-executing `load_postgres` for a finished run (0/0/0 changes, `docs/evidence/dev-sandbox/postgres_audit_queries.txt`) and is covered by `test_load_is_idempotent_and_detects_changes`.

**9. Which data-quality check is most likely to catch a change that silently damages model accuracy?**
The **exact row-count checks per layer** (`stg_row_count_baseline` 30,545, `cur_row_count_baseline` 11,558, `mf_row_count_baseline` 2,628), together with the **test-set membership fingerprint**. A changed NA rule, a reordered cleaning step or a different de-duplication choice still yields a valid-looking dataset that passes every schema, null and range check. But it shifts which rows survive and which rows end up in the test set. That is exactly the kind of change that moves accuracy without raising an error. A second, more model-specific guard is `mf_label_matches_who_rule`, which catches a changed threshold or label inversion.

**10. How do you know the training and test rows are the same logical rows used in the baseline?**
The notebook was executed verbatim to compute the sha256 of the sorted `station_day_key`s of its 526 test rows (and of its 2,102 training rows). These are stored in `expected/baseline_metrics.json`. Every pipeline run computes the same fingerprints from its own split. `reproducibility_check` requires an exact match, and both fingerprints match. The predictions file also lists the station-day key of every test row.

**11. What sources of nondeterminism remain?**
Floating-point behaviour across library versions and CPU instruction sets, which is the likely cause of the single 0.0004 difference in Gradient Boosting's CV F1. There is also the operating system and base images: the `python:3.12-slim` and `apache/airflow:2.10.5` tags are pinned but not by digest. Audit timestamps and run ids differ by design, which is why layer fingerprints exclude audit columns. Parallelism is not used (`n_jobs` unset), so thread scheduling has no effect, and every random process is seeded.

**12. If the reproduced metric differs, how do you locate the cause?**
Work outward, using the artifacts the pipeline records. (1) **Data:** source checksum and raw row count (manifest check). (2) **Preprocessing:** `row_counts_by_step` and the staging/curated/feature fingerprints against a known-good run. (3) **Split:** the train/test fingerprints. (4) **Parameters:** `train_config.json` (seed, test size, model parameters, imputation scope). (5) **Dependencies:** `library_versions` in `metrics.json` and the run summary. Re-running in the pinned Docker image isolates this. (6) **Nondeterministic execution:** run twice in the same environment, and if the metrics differ, something is unseeded. The pattern of differences helps too. Here only one model's CV score moved, while every count, the split and all held-out metrics were exact. That points to numerical/library behaviour, not data or split.

**13. What would you monitor if this ran daily in production?**
Freshness and arrival (did a new snapshot arrive; checksum changed as expected), row counts per layer against trailing ranges, null and duplicate rates, the share of rows dropped by each cleaning step, quarantine events, value distributions and drift (PSI or KS) for the eight features and for PM2.5, class balance, model metrics on newly labelled data, prediction-rate drift (share predicted Unhealthy), task durations and retries, load-log inserted/updated/deleted counts, and DQ warnings trending up. I would alert on any failed error-severity check and on drift beyond thresholds.

**14. What becomes the first bottleneck at 100× data?**
The pandas-in-memory transforms and the full recomputation of staging and curated from all raw batches on every run: the pivot, de-duplication and fingerprints over about 5 million readings in one process, inside a single LocalExecutor container. The full-snapshot `COPY` plus upsert of the whole table each run would follow. The fixes: incremental staging and curated merges by partition (date or country), a columnar engine (DuckDB, Polars or Spark), loading only changed partitions, and a distributed executor.

**15. What changes if the dataset became sensitive or regulated?**
Encrypt at rest and in transit (TLS to PostgreSQL), keep secrets in a secrets manager rather than `.env`, and use least-privilege database roles (separate loader, reader and auditor roles, plus row-level security if needed). Classify columns, and pseudonymise or remove direct identifiers before staging, keeping a protected key table. Document lawful basis, retention and deletion (raw batches and quarantine would need expiry). Restrict who can view raw and quarantine data, and audit access. Stop logging DQ "examples" (they contain row values) or mask them. Do not commit benchmark or evidence files with real values. Review data residency for the containers and backups.
